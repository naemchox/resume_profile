# Co-op Coding

VS Code extension ที่ทำให้หลายคนแก้โฟลเดอร์เดียวกันแบบ real-time โดย
**ไฟล์ยังเป็นไฟล์จริงบนดิสก์ของทุกคน** — ใครจะ `npm run dev` หรือเปิด Live Server
ของตัวเองก็ได้ ไม่ต้องมี host และไม่ต้องรอใคร

co-op จะ **ออนไลน์เองเมื่อมีคนแรกเข้า และดับเองเมื่อคนสุดท้ายออก**

---

## ลองเลย

```bash
# 1. เปิดเซิร์ฟเวอร์ (terminal ที่ 1) - ตัวเดียวกับบน Cloudflare รันในเครื่องที่ ws://localhost:8787
./start-server.sh

# 2. เปิด VS Code สองหน้าต่าง Alice กับ Bob (terminal ที่ 2)
./open-test-windows.sh
```

สองหน้าต่างถูกตั้งให้ชี้ไปเซิร์ฟเวอร์ในเครื่องให้แล้ว ล้างโปรไฟล์ทดสอบได้ด้วย `./open-test-windows.sh reset`

**ในหน้าต่าง Alice** (เจ้าของ = เครื่องหลัก) — กดไอคอน Co-op ทางซ้าย หรือคลิก `Co-op: offline` มุมซ้ายล่าง → `สร้าง co-op จากโฟลเดอร์นี้`
→ ตั้งชื่อ → เลือก **คัดลอก invite (แก้ไขได้)** invite code จะอยู่ใน clipboard แล้ว

**ในหน้าต่าง Bob** — คลิก `Co-op: offline` → `เข้าด้วย invite code` → วาง

จากนั้นเปิด `index.html` ทั้งสองฝั่งแล้วพิมพ์พร้อมกัน

ลองระดับ **อ่านอย่างเดียว** ได้ด้วย: ที่ Alice เลือก `คัดลอก invite ให้เพื่อน` → `อ่านอย่างเดียว`
ฝั่งที่เข้าด้วย invite นั้นจะพิมพ์ได้ในเครื่องตัวเอง แต่ไม่มีใครเห็น และเซิร์ฟเวอร์ปฏิเสธตั้งแต่ต้นทาง

## invite code กับสิทธิ์

co-op มีสามระดับ แต่ละระดับมี token ของตัวเอง invite code หนึ่งอันคือ token หนึ่งอัน

| ระดับ | ทำอะไรได้ |
|---|---|
| owner | แก้ได้ + ออก invite ให้คนอื่น + ยกเลิก invite |
| editor | แก้ได้ |
| viewer | อ่านได้อย่างเดียว เห็น cursor คนอื่น และคนอื่นเห็น cursor ของเขา |

- **invite code หน้าตาแบบนี้** `COOP1-eyJzIjoid3M6...` — ข้างในมีที่อยู่เซิร์ฟเวอร์ + id ของ co-op + token
  เพื่อนวางอันเดียวจบ ไม่ต้องตั้งค่าอะไรเพิ่ม
- **token ไม่ได้เก็บใน `.vscode/settings.json`** แต่เก็บใน SecretStorage ของ VS Code
  เพราะ settings อยู่ในโฟลเดอร์และมีสิทธิ์ติดขึ้น git ไปด้วย
- **ห้าม commit `server/data/coops.json`** — มี token ทั้งหมดของทุก co-op (ใส่ .gitignore ไว้แล้ว)
- **invite หลุดแล้วยกเลิกได้** `ยกเลิก invite เดิมแล้วออกใหม่` คนที่ถือของเก่าจะเข้าไม่ได้ทันที
- **การจำกัดสิทธิ์บังคับที่เซิร์ฟเวอร์ ไม่ใช่ที่ client** เพราะ client คือโค้ดที่อยู่ในมือคนอื่น

## เครื่องเจ้าของห้องคือตัวหลัก

| เกิดอะไรขึ้น | ผล |
|---|---|
| เจ้าของแก้ / สร้าง / ลบไฟล์ **นอก co-op** (โปรแกรมอื่น, git, Finder) | เข้าห้องเอง ไฟล์ของทุกคนเปลี่ยนตาม |
| ใครก็ตามพิมพ์ในห้อง | ทุกคนเห็นสดในจอ แต่ **ยังไม่ลงดิสก์ของใคร** |
| ใครก็ตามกด **เซฟ** | ไฟล์บนดิสก์ของทุกคน (รวมเครื่องเจ้าของ) เปลี่ยนตาม |
| เจ้าของแก้ไฟล์นอก co-op ขณะที่ในห้องมีงานที่ยังไม่เซฟ | ไม่ทับให้ ขึ้นเตือนทุกคนที่แก้ได้ เลือก "ใช้ของเครื่องเจ้าของ" / "เก็บงานในห้อง" / "ดูความต่าง" คนแรกที่ตอบเป็นคนตัดสิน |
| ลบ / เปลี่ยนชื่อไฟล์ใน VS Code | sync ไปทุกเครื่อง ไฟล์ที่ถูกลบตามคนอื่นจะไปอยู่ในถังขยะ ไม่หายถาวร |
| เพื่อนแก้ไฟล์ในเครื่องตัวเอง **นอก co-op** | ไม่สนใจ โฟลเดอร์ของเพื่อนเป็นแค่สำเนา |
| เจ้าของกลับเข้าห้องแล้วไฟล์ไม่ตรง (แก้ไว้ระหว่างไม่อยู่) | ถามว่าจะ "ใช้ของเครื่องฉัน" หรือ "ใช้ของ co-op" |

ตอนกด **สร้าง co-op** ในโฟลเดอร์ที่มีห้องอยู่แล้ว จะถามก่อนว่าจะกลับเข้าห้องเดิม หรือสร้างห้องใหม่แทน
ถ้าสร้างใหม่ ห้องเดิมจะถูกปิด คนที่ถือ invite เก่าจะได้ข้อความ "ห้องถูกปิด ขอ invite ใหม่" แทนที่จะเข้าไปในห้องว่าง
(ต้องใช้เซิร์ฟเวอร์รุ่นใหม่ - deploy ใหม่หลังอัปเดต)

## แถบด้านข้าง

ไอคอน Co-op บน activity bar (แบบเดียวกับ Live Share) มีสองส่วน

- **ห้องที่อยู่ตอนนี้** — ชื่อห้อง สิทธิ์ ผู้เข้าร่วม และไฟล์ที่แต่ละคนเปิดอยู่ กดที่ชื่อเพื่อนเพื่อไปดูตรงที่เขาอยู่
  ถ้ายังไม่อยู่ในห้องจะมีปุ่ม สร้างห้อง / เข้าด้วย invite code
- **ห้องทั้งหมดของฉัน** — ทุกห้องที่เคยสร้างหรือเข้าบนเครื่องนี้ บอกว่ามีใครออนไลน์ หรือห้องถูกปิดแล้ว
  กดเพื่อสลับห้อง (หน้าต่างนี้จะเปิดโฟลเดอร์ของห้องนั้นแล้วเข้าให้เอง) หรือกดปุ่มหน้าต่างเพื่อเปิดในหน้าต่างใหม่

### ไฟล์ของเรากับของเพื่อนตรงกันไหม

`Co-op: เทียบไฟล์กับ co-op` เทียบโฟลเดอร์บนเครื่องคุณกับ Y.Doc ที่แชร์อยู่
ไม่ได้เทียบกับเครื่องเพื่อนโดยตรง — เพราะทั้งสองฝั่ง sync กับ Y.Doc ตัวเดียวกัน
ถ้าต่างคนต่างเทียบแล้วผ่านทั้งคู่ ก็แปลว่าไฟล์ตรงกัน และเพื่อนไม่ต้องรันอะไรให้

ผลลัพธ์แยกเป็นสี่กอง กดที่ไฟล์เพื่อเปิดดูได้

| กอง | แปลว่า |
|---|---|
| เนื้อหาไม่ตรง | เปิด diff เทียบฉบับ co-op กับฉบับบนเครื่องคุณ |
| มีใน co-op แต่ไม่มีบนเครื่องคุณ | มักเกิดจากลบไฟล์ทิ้งนอก VS Code ในเครื่องเพื่อน (เครื่องเพื่อนไม่ถูกนับเป็นตัวหลัก) |
| มีบนเครื่องคุณ แต่ไม่ได้อยู่ใน co-op | เพื่อนไม่เห็นไฟล์นี้ |
| ใหญ่หรือเป็น binary เกินกว่าจะ sync | เกิน 1 MB หรือไม่ใช่ข้อความ — ตั้งใจให้ข้าม |

ไฟล์ที่เปิดค้างอยู่จะเทียบจากสิ่งที่อยู่ในจอ ไม่ใช่สิ่งที่อยู่บนดิสก์
ของที่พิมพ์ไว้แต่ยังไม่ save จึงนับว่า "ไม่ตรง" ตามความจริง

สองกองแรกซ่อมได้ในที่: ชี้ที่แถวแล้วกดปุ่มดาวน์โหลดท้ายแถว เพื่อเอาฉบับ co-op มาทับ
หรือเลือกแถวบนสุดเพื่อทับทั้งหมดรวดเดียว ถามยืนยันก่อนทุกครั้ง
**ไฟล์ที่ไม่ได้เปิดค้างไว้จะเขียนลงดิสก์ตรง ๆ กู้ด้วย undo ไม่ได้**

**ทุกครั้งที่เข้า co-op สำเร็จ ตัวแอปเทียบให้เองอยู่แล้ว** ถ้าไม่ตรงจะถามว่าจะเอาฉบับ co-op มาทับไหม
ถามเฉพาะสองกองแรกเท่านั้น — กอง "ไฟล์ของคุณเอง" กับ "ใหญ่เกินจะ sync" เป็นเรื่องปกติของทุกโฟลเดอร์
ถ้าเตือนทุกครั้งคนจะเลิกอ่านคำเตือน ปิดได้ที่ `coop.verifyOnJoin`

### ชื่อที่เพื่อนเห็น

`Co-op: เปลี่ยนชื่อที่เพื่อนเห็น` เปลี่ยนชื่อข้าง cursor ของคุณ
ถ้ากำลังอยู่ใน co-op ทุกเครื่องจะเห็นทันที ไม่ต้องออกแล้วเข้าใหม่
(ชื่ออยู่ใน awareness ซึ่งเป็นการกระจายสด ไม่ใช่ส่วนหนึ่งของเอกสาร)
ชื่อเก็บไว้ในเครื่องคุณ ไม่ได้ผูกกับ co-op จึงติดตัวไปห้องถัดไปด้วย

## เทสต์

```bash
# ยิงใส่ตัวไหนก็ได้ - ใส่ env var ชี้เป้า
H=https://your-server.workers.dev
W=wss://your-server.workers.dev

HTTP=$H WSURL=$W node server/smoke-test.mjs        # sync + สิทธิ์ (15 ข้อ)
cd extension && COOP_SERVER=$W npm run check:invite # invite code ฝั่ง client (13 ข้อ)
cd worker && HTTP=$H WSURL=$W node persist-test.mjs # งานไม่หายเมื่อทุกคนออก (3 ข้อ)
cd worker && npm run test:limits                    # กันการใช้ในทางที่ผิด (7 ข้อ, local เท่านั้น)
cd extension && npm run check:folders               # กติกาชื่อโฟลเดอร์ (17 ข้อ, ไม่ต้องมีเซิร์ฟเวอร์)
cd extension && npm run check:verify                # เทียบ/ดึงไฟล์ + เปลี่ยนชื่อ (23 ข้อ, ไม่ต้องมีเซิร์ฟเวอร์)
cd extension && COOP_SERVER=$W npm run check:sync   # เจ้าของ+เพื่อน: เซฟ, ชนกัน, ลบ, ปิดห้อง (25 ข้อ)
```
ทั้งสองชุดไม่ต้องเปิด VS Code เลย ใช้แยกว่าปัญหาอยู่ฝั่งไหนได้เร็วมาก


## เซิร์ฟเวอร์

ตอนนี้ deploy อยู่บน **Cloudflare Workers + Durable Objects (แผนฟรี)**

```
wss://your-server.workers.dev
```

หนึ่ง co-op = หนึ่ง Durable Object ซึ่ง Cloudflare การันตีว่ามี instance เดียวในโลก
เลยไม่มีทางเกิด split brain และไม่ต้องตั้ง sticky routing เอง

**Hibernation คือสิ่งที่ทำให้ฟรีจริง** — co-op ที่ไม่มีใครพิมพ์อยู่จะถูกถอดออกจาก RAM
และไม่กินโควตาเลย ตื่นเองเมื่อมีข้อความเข้ามา แต่ตอนตื่นมันจะลืมทุกอย่างใน RAM
เราเลย **ต้อง** เขียน Yjs doc ลง storage ซึ่งได้ผลพลอยได้คือ co-op รอดแม้ทุกคนออกหมด

โควตาแผนฟรี: 100,000 requests/วัน (WebSocket นับแค่ตอนต่อครั้งแรก ไม่ใช่ทุกข้อความ),
13,000 GB-s/วัน, storage 5 GB, เขียน 100,000 แถว/วัน
การเขียน doc ลง storage debounce ไว้ 2 วินาที เพื่อไม่ให้ชนโควตาเขียน

```bash
cd worker
npm run dev            # รันในเครื่อง (ไม่ต้องล็อกอิน) ที่ localhost:8787
npm run deploy         # ขึ้นคลาวด์
npm run tail           # ดู log ตัวจริง
```




## เซิร์ฟเวอร์เป็นของคนที่ host เอง

extension ที่แจกออกไป **ไม่มีที่อยู่เซิร์ฟเวอร์ติดมาด้วย** (`coop.serverUrl` ว่างเปล่า)
ถ้าใส่ default ไว้ คนที่ตั้ง default นั้นจะกลายเป็นผู้ให้บริการและผู้ดูแลข้อมูล
ของคนแปลกหน้าทุกคนที่โหลดไป ทั้งที่ไม่ได้ตั้งใจ

**คนที่จะสร้าง co-op** สั่ง `ตั้งเซิร์ฟเวอร์ของฉัน (Cloudflare)` ครั้งเดียว
→ เปิดหน้า authorize ของ Cloudflare → กดอนุญาต → extension ส่ง worker ขึ้นบัญชีเขาเอง
→ ได้ที่อยู่ `wss://coop-coding-server.<ชื่อเขา>.workers.dev` เก็บลง settings ให้อัตโนมัติ

**คนที่เข้าด้วย invite ไม่ต้องทำอะไรเลย** ไม่ต้องมีบัญชี Cloudflare ไม่ต้องตั้งค่า
เพราะ invite code พกที่อยู่เซิร์ฟเวอร์ของเจ้าของห้องมาให้แล้ว — ตั้งครั้งเดียวต่อกลุ่ม

### ทำไมใช้ Wrangler แทน OAuth ของเราเอง

Cloudflare เปิดให้จด OAuth client ของตัวเองได้แล้ว แต่จะให้คนทั่วไปกด authorize ได้
ต้อง promote client เป็น public ซึ่ง **ต้องยืนยันโดเมนด้วย DNS TXT และกดแล้วย้อนไม่ได้**
ระหว่างที่ยังไม่มีโดเมน การเรียก `wrangler login` ให้ผลลัพธ์แบบเดียวกัน
คือหน้า authorize ทางการของ Cloudflare และ **ไม่มี credential อะไรฝังอยู่ใน `.vsix` เลย**
แลกกับการที่เครื่องผู้ใช้ต้องมี Node (ซึ่งคนใช้ VS Code ส่วนใหญ่มีอยู่แล้ว)

worker ถูก bundle เป็นไฟล์เดียว 254 KB ติดไปกับ `.vsix` (`out/worker/worker.js`)
จึง deploy ได้โดยไม่ต้อง `npm install` บนเครื่องผู้ใช้ และไม่ต้องใช้ `nodejs_compat`

## ไฟล์ของคนที่ join ไปอยู่ไหน

คนที่ **สร้าง** co-op ทำงานในโฟลเดอร์ตัวเองตามปกติ ไม่มีอะไรเปลี่ยน

คนที่ **join** จะถูกถามเสมอว่าจะวางไว้ที่ไหน โดยมีที่ประจำชื่อ `coop session`

```
<ที่ที่เลือกไว้>/coop session/
├── Websites/        ← co-op แรกที่ join
└── OtherProject/    ← co-op ที่สอง
```

- ครั้งแรก: ยังไม่มี `coop session` → ให้เลือก path แล้ว extension สร้างให้
- ครั้งต่อไป: เจอที่ประจำแล้ว เสนอเป็นค่าเริ่มต้น กดยืนยันอย่างเดียว (เปลี่ยนที่ได้ตลอด)
- ชื่อโฟลเดอร์ย่อยมาจาก **ชื่อโฟลเดอร์ต้นฉบับของคนสร้าง** ซึ่งเซิร์ฟเวอร์เก็บไว้ให้
- join co-op เดิมซ้ำ จะกลับเข้าโฟลเดอร์เดิมเสมอ ไม่สร้างซ้ำ
- ชื่อชนกับโฟลเดอร์ที่มีอยู่แล้ว **จะถาม** ว่าจะใช้ของเดิมหรือสร้าง `ชื่อ (2)` แยก
  (เดิมเติม `(2)` ให้เงียบ ๆ ซึ่งผิด เพราะกด "สร้าง co-op" ใหม่ทุกครั้งจะได้ id ใหม่เสมอ
  ต่อให้เป็นโฟลเดอร์เดิม เพื่อนเลยได้ `startup (2)`, `(3)` กองไปเรื่อย ๆ)

**ทำไมต้องทำแบบนี้:** ตอน join **co-op ชนะเสมอ** ไฟล์ชื่อซ้ำจะถูกเขียนทับ
ถ้าปล่อยให้คน join เอาโฟลเดอร์งานตัวเองมาเป็นเป้า งานเขาจะหาย
การบังคับให้ลงใน `coop session` เลยเป็นการกันอุบัติเหตุนั้นตั้งแต่ต้นทาง

การ join ต้องเปิดโฟลเดอร์อื่น ซึ่งทำให้ extension host เริ่มใหม่ — invite เลยถูกฝากไว้
ใน globalState ก่อน แล้วหน้าต่างใหม่ค่อยหยิบไปใช้ต่อ (ดู `resumePendingJoin`)
และเพราะไม่ต้องมีโฟลเดอร์เปิดอยู่ก่อนแล้ว **join จากหน้าต่าง VS Code เปล่า ๆ ได้เลย**

## กันการใช้ในทางที่ผิด

บังคับที่ฝั่ง Worker ทั้งหมด (ตัว node ใน `server/` **ไม่มี** ส่วนนี้ — อีกจุดที่ drift กัน)

| กัน | เพดาน | ทำยังไง |
|---|---|---|
| ยิงสร้าง co-op รัว | 20/ชม. และ 100/วัน ต่อ IP | Durable Object หนึ่งตัวต่อหนึ่ง IP นับแบบ fixed window |
| เดา invite | ผิดได้ 10 ครั้ง/10 นาที ต่อ IP ต่อ co-op | นับใน Coop DO เอง |
| คนใน co-op เดียว | 32 WebSocket | เช็คตอน upgrade |
| ขนาด co-op | 25 MB แล้วกลายเป็นอ่านอย่างเดียว | เช็คตอน persist |
| body ที่ส่งมา | 4 KB | เช็ค content-length + ความยาวจริง |

ปรับเพดานการสร้างได้โดยไม่ต้องแก้โค้ด: ตั้ง var `CREATE_PER_HOUR` / `CREATE_PER_DAY`

**เรื่องที่ต้องระวังเป็นพิเศษ: จะรู้ได้ยังไงว่าใครเป็นใคร**
ใช้ `CF-Connecting-IP` เท่านั้น เพราะ Cloudflare เป็นคนเขียนให้ที่ edge ปลอมไม่ได้
ส่วน `X-Forwarded-For` ปลอมง่ายมาก (ใครก็ใส่เองได้) เลยอ่านเฉพาะตอนที่ `CF-Connecting-IP`
เป็น loopback ซึ่งเกิดขึ้นเฉพาะใน `wrangler dev` เท่านั้น — ทำให้เทสต์แกล้งเป็นหลายคนได้
โดยที่ production ไม่มีช่องให้ปลอม

โดนกั้นแล้วจะได้ `429` พร้อมหัว `Retry-After` และ `retryAfterSeconds` ในเนื้อ
เพื่อให้ client บอกผู้ใช้ได้ว่าให้รอนานเท่าไร

```bash
cd worker && npm run dev              # terminal หนึ่ง
cd worker && npm run test:limits      # terminal สอง - รันกับ local เท่านั้น
```
รันกับ production ไม่ได้ เพราะมันจะกินโควตาจริงของคุณและทิ้ง co-op ขยะไว้เป็นสิบ

### `server/` คืออะไร

เป็นเวอร์ชัน node ที่เขียนไว้ตอนแรก **ไม่ใช่ตัวที่ deploy แล้ว** เก็บไว้เพราะรันง่ายตอน dev
และ `smoke-test.mjs` ใช้ร่วมกันได้ทั้งสองตัว ข้อควรระวังคือถ้าแก้ฝั่งหนึ่งแล้วไม่แก้อีกฝั่ง
มันจะ drift กัน — ถ้าไม่ได้ใช้แล้วลบทิ้งได้เลย (ตัว node ไม่ persist งาน ต่างจาก worker)

## ตอนนี้ทำอะไรได้ / ยังทำไม่ได้

ทำได้แล้ว
- แก้ไฟล์เดียวกันพร้อมกัน merge ถูกต้อง (Yjs CRDT)
- เห็น cursor + selection + ชื่อของคนอื่น
- join แล้วดึงไฟล์ทั้งโฟลเดอร์ลงเครื่องอัตโนมัติ
- เขียนลงดิสก์ให้เองหลังรับ remote edit → dev server/Live Server เห็นทันที
- หลุดเน็ตแล้วกลับมา ตามงานที่พลาดไปได้ครบ
- co-op ตื่นเอง/ดับเอง
- ไม่ sync: `node_modules`, `dist`, `build`, `.env*`, โฟลเดอร์ที่ขึ้นต้นด้วยจุด, ไฟล์ binary, ไฟล์เกิน 1MB

ทำได้แล้ว (รอบ invite code)
- invite code อันเดียวจบ พกที่อยู่เซิร์ฟเวอร์ไปด้วย
- สามสิทธิ์: owner / editor / viewer บังคับที่เซิร์ฟเวอร์
- ปฏิเสธตั้งแต่ตอน websocket upgrade — คนไม่มี invite ไม่เห็นข้อมูลแม้แต่ไบต์เดียว
- ยกเลิก invite ที่หลุดได้
- token เก็บใน SecretStorage ไม่ใช่ settings
- metadata ของ co-op อยู่รอดแม้ co-op ออฟไลน์ (invite ที่แจกไปแล้วยังใช้ได้)
- **งานใน co-op persist จริง** ทุกคนออกหมดแล้วกลับมา งานยังอยู่ครบ (ได้มาตอนย้ายขึ้น Durable Objects)
- เซิร์ฟเวอร์อยู่บนเน็ตแล้ว เพื่อนคนละที่เข้าได้ ผ่าน `wss://` เข้ารหัส
- กันการยิงสร้าง co-op รัว, เดา invite รัว, คนล้น co-op, และ co-op บวมเกินขนาด

ยังไม่ได้ทำ
- **ลบ / เปลี่ยนชื่อไฟล์** ยังไม่ sync (ถังขยะก็ยังไม่มี)
- แก้ไฟล์จากนอก VS Code (เช่น `git pull`) ยังไม่ถูกจับ — ยังไม่มี file watcher
- ตอน join ใครมีไฟล์ชื่อซ้ำ **co-op ชนะเสมอ** ยังไม่มีให้เลือก
  (คนที่ join ไม่โดนผลนี้แล้ว เพราะลงใน `coop session` ที่ว่าง — แต่คนสร้างยังโดนอยู่ถ้า rejoin)
- ยังไม่มี pause sync ตอนสลับ branch

## บทเรียนที่เจอแล้ว (อย่าพลาดซ้ำ)

- **`import * as WS from 'ws'` แล้วส่งให้ `WebSocketPolyfill` ตรง ๆ จะพัง**
  (`provider._WS is not a constructor`) เพราะได้ module namespace ไม่ใช่ตัว class
  ต้องหยิบ `WS.WebSocket` ออกมา — โค้ดตอนนี้เผื่อไว้ทั้งสามรูปแบบแล้ว
- **extension พังเงียบได้** ถ้าไม่ครอบ try/catch ตอน join — status bar จะดูปกติทั้งที่ไม่ได้ต่อ
  ตอนนี้เด้ง error message ให้แล้ว
- ตรวจ sync ได้โดยไม่ต้องเปิด VS Code ด้วย `node server/smoke-test.mjs`
  แยกว่าปัญหาอยู่ที่ฝั่ง sync หรือฝั่ง editor ได้เร็วมาก
- ถ้าจะตรวจว่า bundle ทำงานจริงไหม ให้เขียนไฟล์ทดสอบไว้ใน `extension/src/`
  แล้ว bundle ด้วย flag ชุดเดียวกับตอน build จริง — ไม่งั้นไม่เจอบั๊กที่เกิดจาก interop
- **route ของ HTTP ต้องเช็คความยาว path ด้วย** ไม่งั้น `/api/coops/:id` จะกลืน
  `/api/coops/:id/invite` แล้วตอบ 200 พร้อมข้อมูลผิดชุด — เจอมาแล้วตอนทำ invite
- **Workers ไม่มี `http`/`ws` ของ node** — ต้องใช้ `WebSocketPair` + `ctx.acceptWebSocket()`
  ส่วน `yjs`/`y-protocols`/`lib0` เป็น JS ล้วน ย้ายมาได้เลยไม่ต้องแก้
- **หลัง hibernation ตัว Durable Object จะรัน constructor ใหม่ด้วย memory เปล่า**
  อะไรที่เก็บใน `Map` จะหาย เลยต้องเก็บ client id ของ awareness ไว้ใน
  `ws.serializeAttachment()` แทน ไม่งั้น cursor ของคนที่ออกไปแล้วจะค้างตลอดกาล
- **workers.dev subdomain ใช้เวลา DNS สักพัก** — deploy เสร็จแล้ว curl ได้ HTTP 000 อยู่หลายนาที
  ไม่ใช่ deploy พัง แค่รอ DNS
- **`wrangler dev` ใส่ `CF-Connecting-IP: ::1` ให้ด้วย** ไม่ได้ปล่อยว่าง ตอนแรกเขียน fallback
  เป็น `CF-Connecting-IP || X-Forwarded-For` เลยกลายเป็นว่า local ทุก request ใช้ bucket เดียวกัน
  เทสต์เรื่อง "คนอื่นไม่โดนลูกหลง" เลย fail — ได้บทเรียนว่าอย่าเดา header ให้ echo ออกมาดูก่อน
- **เทสต์ที่ fail ไม่ได้แปลว่าโค้ดผิดเสมอ** — ข้อ "กันชื่อไต่ออกนอกโฟลเดอร์" fail เพราะไปเช็คว่า
  ผลลัพธ์ห้ามมี `..` ทั้งที่สิ่งที่ต้องรับประกันจริงคือ "ห้ามมี separator และห้ามเป็น `.`/`..`"
  ชื่อ `-..-etc` ปลอดภัยดีอยู่แล้วเพราะเป็นชิ้นเดียว แก้ที่เทสต์ แล้วเขียนข้อห้ามให้ชัดในโค้ดด้วย
- **bundle worker ด้วย `--conditions=workerd,worker,browser`** แล้ว yjs/y-protocols/lib0
  จะเลือก build ฝั่ง browser ให้เอง ไม่ต้องพึ่ง `nodejs_compat` เลย ทดสอบแล้วผ่านทั้ง 18 ข้อ
- **ทดสอบเส้นทาง deploy ด้วยชื่อ worker อื่นเสมอ** (`coop-coding-selftest`) แล้วลบทิ้ง
  ไม่งั้นจะไปทับตัวที่รันอยู่จริงโดยไม่ตั้งใจ
- **co-op id ใหม่ทุกครั้งที่กด "สร้าง"** ต่อให้ชื่อและโฟลเดอร์เดิมเป๊ะ ระบบมองเป็นคนละห้อง
  ตรรกะอะไรที่ผูกกับ "ห้องเดียวกัน" ต้องคิดเผื่อข้อนี้เสมอ
- **ถอน extension ไม่ได้ล้าง SecretStorage และ globalState** VS Code เก็บไว้ตาม extension id
  ลงใหม่แล้วของเก่ากลับมาทั้งหมด — เป็นเหตุที่เครื่องที่ "ลบลงใหม่แล้ว" ยังได้ `startup (3)`
  จึงต้องมีคำสั่งล้างในตัว จะหวังพึ่งการ uninstall ไม่ได้
- **อย่าอ่าน invite จากที่เก็บเมื่อกำลังจะ "คัดลอก invite ของห้องที่อยู่"** เพราะ `leave()`
  ไม่ได้ล้างที่เก็บ ผลคือคัดลอกได้ลิงก์ของห้องที่ออกมาแล้ว ต้องอ่านจาก session ที่ต่ออยู่จริง
- **`connect()` ที่ return เงียบ ๆ ตอนมี session อยู่คือกับดัก** สร้างห้องใหม่แล้ว invite ใหม่
  ไม่ถูกบันทึก ของเก่าค้างอยู่ตลอด แก้เป็นออกจากห้องเดิมแล้วเข้าห้องใหม่แทน
- **mapping โฟลเดอร์ต้องลบตัวที่โฟลเดอร์หายไปแล้วทิ้ง** ไม่งั้นลบโฟลเดอร์ทิ้งแล้วชื่อยังถูกจองอยู่
