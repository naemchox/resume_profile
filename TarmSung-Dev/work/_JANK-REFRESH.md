# กระตุกตอนรีเฟรช — ที่มา วิธีแก้ และรูที่ด่านตรวจมองไม่เห็น
_2026-08-25 · เจ้าของฟ้องจาก Safari · แก้แล้วใน the-bed + the-terrace_

## อาการที่ถูกฟ้อง
1. The Bed — พื้นหลังกับตัวหนังสือบางส่วนกระตุกตอนรีเฟรช
2. The Terrace — แถบตัวเลข (`480+ / 40–300 / ★4.9`) กระตุก

## สาเหตุจริง (วัดแล้ว ไม่ได้เดา)

| # | ต้นเหตุ | ทำไมตาเห็นว่ากระตุก |
|---|---|---|
| 1 | รูปฮีโร่ the-bed เป็น `background-image` ใน CSS | preload scanner อ่านแค่ HTML จึงหาไม่เจอ ต้องรอ CSS จบก่อน รูปมาช้าจนต้องเอา LQIP เบลอ 32px มาคั่น = คนเห็น **เบลอ → ชัด ทุกครั้งที่รีเฟรช** |
| 2 | `font-display: optional` | "มาไม่ทันเฟรมแรก = ใช้ฟอนต์สำรองทั้งรอบโหลด" → **ผลไม่เหมือนกันในแต่ละรีเฟรช** อ่านว่า "เดี๋ยวก็กระตุก เดี๋ยวก็ไม่" |
| 3 | H1 ฮีโร่ `.split` = หั่นเป็นคำ 9 กล่อง `overflow:hidden` | กล่องยืดหดตามฟอนต์ ขณะที่ตัวอักษรยังเคลื่อน |
| 4 | JS รอ `document.fonts.ready` (เพดาน 900ms) ก่อนเล่น | ฮีโร่ค้างว่างได้ถึง 900ms แล้วโผล่พรวด |
| 5 | ตัวเลขนับ `0 → 480` | ตัวหนังสือโตจาก 1 หลักเป็น 3 หลัก **ความกว้างเปลี่ยนทุกเฟรม** ทั้งบรรทัดถูกจัดใหม่ ~60 ครั้ง/วินาที |

**วัดข้อ 5 ได้ตรงๆ** (เลื่อนตำแหน่งของข้อความข้างๆ ระหว่างนับ):

| | ก่อนแก้ | หลังแก้ |
|---|---|---|
| ก้อน `480+` | **11.44 px** | **0.00 px** |
| ประโยค `จาก N รีวิวคู่บ่าวสาว` | **8.40 px** | **0.00 px** |

## วิธีแก้ที่ใช้
- **the-bed**: รูปฮีโร่ → `<img fetchpriority="high" width height>` (ถอด LQIP base64 ทิ้ง) · `optional` → `swap` · H1 `.split` → `.reveal` · เลิกรอ `fonts.ready`
- **ทั้งสองใบ**: `lockWidth()` — จองความกว้างของตัวเลขเป็น `ch` จากค่าจริงที่พิมพ์อยู่ใน HTML ก่อนเริ่มนับ + `tabular-nums`
  - ใช้ `ch` ไม่ใช่ `px` เพราะโหลดฟอนต์แบบ swap — วัดเป็น px ตอนฟอนต์สำรองยังอยู่แล้วจะผิดทันทีที่ฟอนต์จริงมา
  - `tabular-nums` เพียงอย่างเดียว **ไม่พอ** มันแก้แค่ "แต่ละหลักกว้างเท่ากัน" ไม่ได้แก้ "จำนวนหลักเปลี่ยน" — คนละเรื่อง
  - the-bed มี `tabular-nums` + `data-pad` อยู่แล้ว the-terrace **ไม่มีทั้งคู่** = ของชนิดเดียวกันคนละกลไก (ละเมิดกฎ "แก้ประเภท ไม่ใช่แก้ตัวอย่าง") ตอนนี้ใช้กลไกเดียวกันแล้ว

## รูของด่านตรวจ (สำคัญกว่าตัวบั๊ก)
ทั้ง 5 ข้อ **ผ่าน audit หมด** ตอนที่มันยังพังอยู่ เพราะ:

1. **วัดผิดเบราว์เซอร์** — ด่านตรวจรัน Chromium เจ้าของเทส Safari สองตัวได้ไฟล์ฟอนต์คนละไฟล์
   ตีความ `display:optional` คนละแบบ คืนตำแหน่ง scroll คนละจังหวะ (คอมเมนต์ในไฟล์เองเขียนไว้ว่า
   *"จุดบอดของด่านตรวจ ไม่ใช่ของที่ไม่มี"* — รู้อยู่แล้ว แต่ไม่มีใครปิดรู)
2. **CLS จับ "เบลอ → ชัด" ไม่ได้** เพราะไม่มีอะไรเลื่อนตำแหน่ง เปลี่ยนแค่ความคมชัด → เลขเขียว แต่ตาเห็นว่าพัง
3. **ไม่มีด่านไหนวัดการขยับระหว่างอนิเมชัน** วัดแต่สถานะนิ่งก่อน/หลัง

**ด่านที่ควรมี (ยังไม่ได้ทำ):**
- ถ่ายภาพหน้าจอ n เฟรมแรกตอนรีเฟรช แล้วเทียบภาพต่อภาพ → จับ "เบลอ → ชัด" ได้ ซึ่ง CLS จับไม่ได้ตลอดกาล
- สุ่มค่าระหว่างทางของทุก counter แล้ววัด drift ของอีลิเมนต์ข้างเคียง → ต้องเป็น 0 px (ท่าที่ใช้วัดในเอกสารนี้)
- รันบน WebKit ด้วย ไม่ใช่ Chromium อย่างเดียว

# ด่านตรวจตัวใหม่ — `playbook/audit-firstpaint.mjs` (25/8/26)

## หลักคิด: เลิกตรวจ "สาเหตุ" มาตรวจ "คุณสมบัติ"
ด่านเดิมทุกตัวเป็น **ตัวตรวจกฎ** — `audit-motion.mjs` เขียนไว้เองว่า *"ดูจากสาเหตุ ไม่ใช่รอให้เห็นเฟรมตก"*
ซึ่งแปลว่ามันหาได้เฉพาะสาเหตุที่เรารู้จักแล้ว **บั๊กทั้ง 5 ข้อข้างบนไม่มีข้อไหนอยู่ในลิสต์นั้น โดยนิยามจึงหาไม่เจอ**

ตัวใหม่ไม่ถามว่า "ผิดกฎข้อไหน" แต่ถาม **คุณสมบัติที่ต้องจริงเสมอ** 2 ข้อ ซึ่งไม่ต้องรู้สาเหตุล่วงหน้า:

**ด่าน 1 — ปิดอนิเมชันแล้วหน้าต้องนิ่ง**
เปิดด้วย `prefers-reduced-motion: reduce` (ดับการเคลื่อนไหวที่ตั้งใจทิ้งหมด) ถ่ายภาพตั้งแต่ `commit`
ถึง ~1.4 วิ แล้วเทียบทุกใบกับใบสุดท้าย **อะไรที่ยังเปลี่ยน = ของที่ไม่ได้ตั้งใจ**
รูปมาช้า · ฟอนต์สลับ · เลย์เอาต์กระโดด · LQIP เบลอ→ชัด เข้าข่ายหมดด้วยกฎเดียว

**ด่าน 2 — ของที่ไม่ได้เล่นอนิเมชัน ห้ามขยับ**
เก็บ `offsetLeft/Top/Width/Height` (เทียบทั้งเอกสาร) ของทุกอีลิเมนต์ที่มีตัวหนังสือ พร้อมเลื่อนหน้าไปด้วย
ใช้ `offset*` ไม่ใช่ `getBoundingClientRect` **ตั้งใจ** — อนิเมชันที่ทำถูกวิธีเล่นบน `transform` ซึ่งไม่แตะ `offset*`
ค่าที่ขยับจึงแปลว่ามีการจัดเลย์เอาต์ใหม่จริง

**รันบน WebKit เป็นค่าเริ่มต้น** — `grep -l chromium playbook/audit-*.mjs` = ครบทุกไฟล์ · webkit = 0 ไฟล์
เจ้าของเทสบน Safari ด่านทุกตัวจึงตาบอดต่ออาการฝั่ง WebKit มาตลอด

## บทเรียนจากการสร้างด่านนี้ (พลาดจริง จดไว้กันซ้ำ)
1. **วัดแต่รอบรีเฟรชไม่พอ** — รอบแรกวัดแต่รอบแคชอุ่น ด่านขึ้นเขียวให้โค้ดที่พังจริง
   เพราะพอแคชอุ่น รูปกับฟอนต์มาตั้งแต่เฟรมแรก อาการไม่เกิดเลย → ต้องวัด **รอบเย็นด้วยเสมอ**
2. **ห้ามรอ `load` ก่อนเริ่มถ่าย** — กว่ากล้องจะเปิด ของที่ต้องจับจบไปแล้ว ต้องถ่ายตั้งแต่ `commit`
3. **ด่าน 2 ต้องเลื่อนหน้า** — ของที่เล่นตอนเลื่อนถึงอยู่ใต้ขอบจอ ถ้าจอดอยู่บนสุดมันไม่เคยเริ่มวิ่ง
4. **`page.evaluate` ไม่ส่งค่าคงที่ระดับโมดูลไปด้วย** — อ้างแล้วได้ `ReferenceError` ในหน้าเว็บ
   ถ้ามันเกิดใน `setTimeout` จะไม่มีใครจับ promise ไม่ resolve แล้ว evaluate ค้างตลอดกาล
   (`audit-motion.mjs` เตือนเรื่องนี้ไว้แล้ว อ่านแล้วยังพลาดซ้ำ) → ตอนนี้มี `pageerror` + เพดานเวลา
5. **`offsetTop` เทียบ `offsetParent`** ถ้าคลาสไหนเปลี่ยน `position` ตัวเลขกระโดดเป็นบวกปลอม
   ต้องไต่สาย `offsetParent` บวกเอง + กันของที่เป็น `fixed/sticky` ออก
6. **ด่านที่ผ่านทุกอย่างคือด่านไร้ค่า** — ต้องเอาโค้ดก่อนแก้กลับมาวางแล้วพิสูจน์ว่ามันฟ้อง
   รอบแรกไม่ทำขั้นนี้ ได้ด่านที่ขึ้นเขียวให้บั๊กที่เจ้าของเห็นด้วยตาเปล่า

## ของแรกที่ด่านนี้จับได้ = บั๊กที่ผมเพิ่งสร้างเอง
`lockWidth()` รอบแรกตั้ง `display:inline-block` + `text-align:right` ให้ตัวเลขทุกตัวโดยไม่ดูของเดิม
ตัวเลขที่เป็น block อยู่แล้วจึงหดจาก **445px เหลือ 129px** แล้วดันของข้างๆ ไป **134px**
= สร้างบั๊กชนิดเดียวกับที่กำลังแก้อยู่ ผมตรวจเองแล้วไม่เห็น ด่านเป็นตัวจับ

# รีเฟรชกลางหน้าแล้วแวบเห็นฮีโร่ก่อน (25/8/26 · jek ฟ้องจาก The Terrace)

## อาการ
อ่านอยู่กลางหน้า กด Refresh → เห็นหัวเว็บ/ฮีโร่แวบหนึ่ง แล้วค่อยเด้งกลับที่เดิม "หลังจากนาน"

## สาเหตุ (วัดบน WebKit ไม่ได้เดา)
Safari/WebKit **คืนตำแหน่ง scroll หลังอีเวนต์ `load` เท่านั้น** — วัด `scrollY` ที่
DOMContentLoaded ได้ 0 และที่ `load` ก็ยังได้ 0 ทุกหน้าที่ตรวจ (หน้าแรกของเว็บเรา ·
the-terrace · the-bed · homecraft · glow-clinic) แปลว่าตราบใดที่ยังมีรูป/คลิป/ฟอนต์
ค้างท่อ คนอ่านจะนั่งดู "ที่ผิด" อยู่อย่างนั้น เน็ตช้าเท่าไหร่ก็ค้างนานเท่านั้น

| the-terrace · หน่วงไฟล์ 1200ms (เลียนเน็ตจริง) | ก่อน | หลัง |
|---|---|---|
| เฟรมแรกที่มีเนื้อหา | 251ms **ที่ y=0** | 87ms **ที่ y=4000** |
| คืนตำแหน่งเดิมเมื่อ | 1545ms | 87ms |
| **ค้างผิดที่** | **1294ms** | **0ms** |

Chromium ไม่มีอาการนี้ (คืนให้ตั้งแต่ ~30-60ms) — เป็นเหตุผลเดิมซ้ำรอบสอง: ด่านตรวจที่
รันแต่ Chromium มองไม่เห็นสิ่งที่เจ้าของเห็นบน Safari

## วิธีแก้
`playbook/snippets/scroll-restore.html` — สคริปต์ inline ในหัวทุกหน้า (30 หน้า + shell
ของเดโมหลายหน้าอีก 3 ใบ) เก็บตำแหน่งเองใน `sessionStorage` แล้ววางกลับตั้งแต่จังหวะแรก
ที่หน้าสูงพอ ผ่าน 4 ทางพร้อมกัน (setTimeout(0) · rAF · readystatechange · DCL) แล้วแต่ว่า
ทางไหนมาก่อน — **ไม่ต้องรอรูปโหลดจบ** และหยุดทันทีถ้าผู้ใช้ขยับเอง

ข้อควรระวังที่เจอระหว่างทาง:
- `html { scroll-behavior: smooth }` ทำให้การวางกลับกลายเป็น "ไถ" ให้เห็น → ปิดชั่วคราวตอนวาง
- ให้สายเดียวนัดทั้ง `setTimeout` และ `rAF` = จำนวนนัดโตเป็น 2^n → แยกเป็นสองสาย สายละนัด
- summit ค้างที่ 2979 แทน 3000 ตลอดกาล = scroll anchoring ของเบราว์เซอร์เลื่อนชดเชยให้
  เนื้อหาที่ตาเห็นอยู่กับที่ (ถูกแล้ว) ด่านตรวจจึงยอมคลาด 40px

## ด่านตรวจ
`playbook/audit-scroll-restore.mjs` — WebKit + หน่วงไฟล์ 1200ms, เลื่อนไป 3000px, รีเฟรช,
บังคับว่า `scrollY` ตอน DCL ต้องกลับมาที่เดิมแล้ว · ของเดิมตก 3/3 หน้าที่ลอง · ของใหม่ผ่าน 11/11

## ต่อเนื่อง: หัวเว็บ "โผล่" ตอนรีเฟรชกลางหน้า (25/8/26 · jek ฟ้องจาก The Bed)
พอคืนตำแหน่ง scroll ได้แล้ว อาการถัดมาคือแถบเมนูค่อยๆ ทึบขึ้นและเส้นทองค่อยๆ เข้ม
ให้เห็นทุกครั้งที่รีเฟรช ทั้งที่ผู้ใช้ไม่ได้เลื่อนอะไรเลย — วัดที่ the-bed: **21 ขั้นสี ใน ~360ms**
(พื้นอยู่บน `.nav-shell::before` opacity 300ms · เส้นอยู่บน border-color 400ms)

แก้ในสคริปต์คืนตำแหน่งตัวเดิม: ระหว่างช่วงคืนตำแหน่ง ปิดทรานซิชันของหัวเว็บ (`html.nav-instant`)
แล้วใส่คลาสสถานะให้หัวเว็บในจังหวะเดียวกับที่วาง scroll — ไม่ต้องรอสคริปต์ท้าย `<body>` ของหน้า
(ช้ากว่ากันราว 20ms = เห็นแถบเปล่าได้ 1 เฟรม) · เปิดทรานซิชันคืนทันทีที่ผู้ใช้ขยับเอง
หรืออย่างช้า 900ms การเลื่อนของจริงจึงยังไล่สีลื่นเหมือนเดิม (วัดแล้ว 9 ขั้น)

**หัวเว็บของแต่ละใบใช้คนละคลาส** (drift ที่มีมาก่อน): `.site-header.scrolled` >8px (เว็บเรา) ·
`.nav-shell.scrolled` >40px (the-bed) · `.site-header.stuck` sentinel (the-terrace) ·
`header.small` >120px (homecraft/lumen/glow-clinic) — สคริปต์ใส่ให้ครบทุกแบบ เดาพลาดก็ไม่เป็นไร
เพราะสคริปต์ของหน้าคำนวณทับในเฟรมถัดไปแบบไม่มีทรานซิชัน

| the-bed · รีเฟรชที่ y=2500 | ก่อน | หลัง |
|---|---|---|
| จำนวนขั้นสีของหัวเว็บใน 800ms แรก | 21 | **1** (สถานะสุดท้ายตั้งแต่เฟรมแรก) |

ด่าน `audit-scroll-restore.mjs` เพิ่มข้อ 2: หัวเว็บต้องมีสถานะเดียวใน 800ms แรกหลังรีเฟรช
