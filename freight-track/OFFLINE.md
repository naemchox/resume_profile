## ผลทดสอบที่ทำให้สรุปแบบนี้ (20 ก.ย. 2026)

### ด่าน 1 — เปิดแอปตอนไม่มีเน็ต → ไม่ขึ้นเลย

เปิดหน้าคนขับตอนเน็ตปกติ → ตัดการเชื่อมต่อ → กดรีเฟรช → **ได้หน้า error ของ Chrome**

**สาเหตุ:** โปรเจกต์ไม่มี service worker (ไม่มี `sw.js` ไม่มี `manifest.json`)
เบราว์เซอร์ต้องโหลด HTML/CSS/JS ใหม่จากเซิร์ฟเวอร์ทุกครั้ง และ Firebase SDK ยังโหลดจาก
`gstatic.com` อีกต่อหนึ่ง (`js/firebase.js:13–21`)

> อันตรายกว่าที่คิด: คนขับแค่สลับไปเปิด LINE แล้วกลับมา ถ้าระบบมือถือคืนหน่วยความจำไปแล้ว
> = แอปโหลดใหม่ = เปิดไม่ได้ ไม่จำเป็นต้องปิดแอปเองด้วยซ้ำ

### ด่าน 2 — งานที่ทำตอนออฟไลน์ ถูกทับทิ้ง

จำลองงานที่บันทึกลงเครื่องแล้วแต่ยังไม่ขึ้นคลาวด์ → เปิดแอปใหม่ตอนเน็ตกลับมา → ผลคือ

```
หมายเหตุที่ทำตอนออฟไลน์:  (ว่าง)        ← หายไป
เหตุการณ์ที่บันทึกไว้:      หายไปแล้ว
```

**สาเหตุ:** `js/store.js` → `applyFromCloud()` ทำ `db[name] = rows`
คือเอาข้อมูลจากคลาวด์**ทับทั้งคอลเลกชัน** ตามคอมเมนต์ในโค้ดเองว่า
*"Firestore เป็นตัวจริง — ของที่ส่งมาทับแคชในเครื่องเสมอ"*

ซึ่งถูกต้องถ้าทุกเครื่องออนไลน์ตลอด แต่พังทันทีเมื่อมีงานที่เกิดขึ้นเฉพาะในเครื่อง

## รายการที่ต้องแก้ (เรียงตามลำดับที่ควรทำ)

### 1. เปิด offline persistence ของ Firestore

**ตอนนี้:** `js/firebase.js:35` ใช้ `getFirestore(app)` เปล่า ๆ
งานที่ค้างส่งจึงอยู่ใน**หน่วยความจำของแท็บนั้นเท่านั้น** ปิดแอปเมื่อไหร่หายทันที

**ต้องเปลี่ยนเป็น**

```js
import { initializeFirestore, persistentLocalCache, persistentMultipleTabManager }
  from 'https://www.gstatic.com/firebasejs/10.13.2/firebase-firestore.js';

db = initializeFirestore(app, {
  localCache: persistentLocalCache({ tabManager: persistentMultipleTabManager() })
});
```

**ระวัง:** ต้องเรียกก่อนใช้ `db` ครั้งแรกเสมอ และต้องใช้ `initializeFirestore` ไม่ใช่ `getFirestore`
ถ้าเรียกผิดลำดับจะ throw

### 2. ทำ service worker ให้เปิดแอปได้ตอนไม่มีเน็ต

**ต้องแคช:** `*.html` · `css/*.css` · `js/*.js` · ฟอนต์ · **และ Firebase SDK**

**ระวัง:** SDK ตอนนี้โหลดจาก `gstatic.com` ซึ่งเป็นคนละโดเมน
ทางที่ชัวร์กว่าคือ**ดาวน์โหลดไฟล์ SDK มาไว้ในโปรเจกต์** แล้ว import จาก path ในเครื่อง
จะได้แคชได้แน่นอนและไม่ผูกกับ CDN

**กลยุทธ์แคชที่เหมาะ:** ตัวแอป (HTML/JS/CSS) ใช้ *stale-while-revalidate*
ส่วนข้อมูลอย่าแคชผ่าน service worker ปล่อยให้ Firestore จัดการเอง

### 3. ✅ หยุดไม่ให้คลาวด์ทับงานที่ยังไม่ได้ซิงก์ — **แก้แล้ว 20 ก.ย.**

> **สรุปสิ่งที่ทำ:** เพิ่ม "กล่องขาออก" ใน `js/store.js` เก็บรหัสเอกสารที่ยังไม่ขึ้นคลาวด์
> ลง `localStorage` คีย์ `ft.outbox.v1` · `applyFromCloud()` ห้ามทับเอกสารที่อยู่ในกล่อง ·
> ส่งต่อเองอัตโนมัติเมื่อเปิดแอปใหม่หรือเมื่อ event `online` มาถึง
>
> **ของที่เพิ่ม:** `markDirty()` (จดตอน `write()` แบบ synchronous) · `mergeEvents()` ·
> `retrySync()` · `pendingCount()` (ไว้ให้หน้าจอเอาไปขึ้นป้ายในข้อ 4)
>
> **ผลทดสอบ 20 ก.ย.:** จำลองแก้ข้อมูลในเครื่องแล้วปิดแอป → เปิดใหม่ตอนเน็ตกลับมา →
> ข้อมูลยังอยู่ครบ · กล่องขาออกว่างเอง · ตรวจ Firestore จากนอกแอปแล้วขึ้นไปจริงทั้งหมายเหตุและไทม์ไลน์
>
> **ตัดสินใจเรื่องชนกัน:** เอกสารในกล่องขาออก ของในเครื่องชนะทุกฟิลด์จนกว่าจะส่งสำเร็จ
> **ยกเว้น `events` ที่รวมสองฝั่ง** (เป็นรายการที่มีแต่เพิ่ม) บันทึกที่แอดมินเพิ่มระหว่างนั้นจึงไม่หาย
> · การแยกชนะรายฟิลด์เต็มรูปแบบยังไม่ได้ทำ ดูหัวข้อ "ข้อจำกัดที่เหลือ" ท้ายเอกสาร

นี่คือข้อที่ทำให้ข้อมูลหายจริง และเป็นข้อที่ต้องรื้อแกนกลาง

**ตอนนี้:** `applyFromCloud()` ใน `js/store.js` ทับทั้งคอลเลกชันทุกครั้งที่ snapshot มาถึง

1. ทุกครั้งที่เขียนข้อมูล บันทึก id ของเอกสารนั้นลงกล่องขาออกที่อยู่ใน IndexedDB
   (ไม่ใช่ตัวแปรในหน่วยความจำ ต้องรอดข้ามการปิดแอป)

4. ส่งสำเร็จแล้วค่อยเอาออกจากกล่อง แล้วปล่อยให้ snapshot ทับได้ตามปกติ

**ข้อดีของโครงปัจจุบันที่ช่วยได้:** `flushChanges()` (แก้เมื่อ 20 ก.ย. ดู `STATUS.md` ข้อ 4.2)
มี "ลายนิ้วมือ" ของสิ่งที่ส่งขึ้นไปแล้วอยู่ในหน่วยความจำอยู่แล้ว
**งานคือย้ายลายนิ้วมือชุดนั้นลง IndexedDB ให้รอดข้ามการปิดแอป** แล้วใช้มันเป็นกล่องขาออกเลย

**กรณีที่ต้องตัดสินใจก่อนลงมือ:** ถ้าแอดมินแก้งานใบเดียวกันบนเว็บระหว่างที่คนขับออฟไลน์อยู่
ใครชนะ? แนะนำ **ให้คนขับชนะเฉพาะฟิลด์ที่คนขับเป็นเจ้าของ** (สถานะ รูป ลายเซ็น พิกัด)
ส่วนฟิลด์ของแอดมิน (ค่ารอบ ปลายทาง เลขบิล) ให้คลาวด์ชนะ — ไม่ใช่ทับกันทั้งใบ

### 5. ✅ ย้ายรูปออกจาก localStorage ไป IndexedDB + ส่งรูปเองอัตโนมัติ — **แก้แล้ว 24 ต.ค.**

> **สรุปสิ่งที่ทำ 24 ต.ค.**
> - `js/photoVault.js` (ใหม่): ก่อนเขียน `ft.db.v1` ลง localStorage ดึง base64 ไปเก็บ IndexedDB (`ft.photos`) เหลือแค่ป้าย `idb:<รหัส>`
>   อ่านกลับแล้วเป็นรูปเดิม โค้ดส่วนอื่นไม่ต้องแก้ · รูปที่ยังเขียน IndexedDB ไม่เสร็จฝาก base64 ไว้ก่อน เขียนเสร็จค่อยแทนเป็นป้าย (ปิดแอปกลางทางรูปไม่หาย)

> - `store.js` รอ `initVault()` (top-level await) ก่อนอ่านฐาน · ทุกที่ที่เขียน localStorage ผ่าน `saveLocal()` ที่เดียว

> - `driver.js`: เลิกเด้งหน้าต่างถาม → `autoUpload()` ส่งเองเมื่อเน็ตกลับ / เปิดแอป / หลังบันทึกงานที่มีรูปค้าง · ไม่ผ่านลองใหม่เอง 20 วิ → 40 → … สูงสุด 5 นาที
>   · `migrateLocalPhotos({ stopOnFail:true })` ใบแรกล้ม = หยุดรอบนั้น (ไม่ไล่รอใบละ 30 วิ) · แถบเหลืองบอกความคืบหน้า มีปุ่ม "ส่งเลย" ไว้กดเอง

**ต้องทำ**
- เก็บรูปที่ยังไม่ได้อัปไว้ใน IndexedDB (โควตาระดับ GB) ไม่ใช่ localStorage
- มีคิวอัปรูปที่ทำงานเองเมื่อเน็ตกลับมา (ต่อยอดจาก `migrateLocalPhotos()` ใน `js/store.js` ได้)
- แก้ `write()` ให้โยน error จริงเมื่อเขียนไม่สำเร็จ ไม่ว่าจะคิดว่าต่อคลาวด์ได้หรือไม่
  *(24 ต.ค. เปลี่ยนเป็นแถบแดงแทนการโยน — ดูสรุปด้านบน)*

## เคสทดสอบที่ต้องผ่านก่อนถือว่าเสร็จ

ทำเสร็จแล้วต้องผ่านทุกข้อนี้ ไม่ใช่แค่ "เขียนโค้ดครบ"

| # | สถานการณ์ | ผลที่ต้องได้ |
|---|---|---|
| 1 | ปิดเน็ต → เปิดแอปคนขับใหม่ทั้งหมด | เข้าแอปได้ เห็นงานของตัวเอง |
| 2 | ปิดเน็ต → ถ่ายรูป 4 ใบ + ให้เซ็น + กดปิดจุดส่ง | ปิดได้ และขึ้นป้ายว่าค้างส่ง |
| 3 | **ปิดแอปทิ้งทั้งที่ยังค้างส่ง → เปิดใหม่ (ยังไม่มีเน็ต)** | งานที่ทำไว้ยังอยู่ครบ |
| 4 | **เปิดเน็ตกลับมา** | ซิงก์ขึ้นคลาวด์เองภายในไม่กี่วินาที ป้ายค้างส่งหายไป |

## ข้อจำกัดที่เหลือหลังแก้ข้อ 3 และ 6

1. **ยังเปิดแอปตอนไม่มีเน็ตไม่ได้** (ข้อ 2) — เป็นตัวบล็อกใหญ่สุดที่เหลือ
   ถ้าคนขับสลับไปเปิด LINE แล้วระบบคืนหน่วยความจำ กลับมาก็เปิดแอปไม่ได้
2. ~~งานค้างส่งรอดข้ามการปิดแอปแล้ว แต่รูปยังไม่รอด (ข้อ 5)~~ — แก้แล้ว 24 ต.ค. รูปอยู่ใน IndexedDB และส่งเอง
3. **ยังไม่มีป้ายบอกคนขับว่ากำลังออฟไลน์ / ค้างส่งกี่งาน** (ข้อ 4) —
   `pendingCount()` ทำไว้ให้แล้วใน `store.js` เหลือแค่เอาไปวาดบนหน้าจอ
4. **การชนกันยังหยาบ** — เอกสารในกล่องขาออก ของในเครื่องชนะทุกฟิลด์ (ยกเว้น `events` ที่รวมกัน)
   ถ้าแอดมินแก้ค่ารอบระหว่างที่คนขับออฟไลน์ ค่ารอบนั้นจะถูกทับกลับเมื่อคนขับซิงก์
   → ทางแก้คือแยกชนะรายฟิลด์ตามเจ้าของ ยังไม่ได้ทำ

## กับดักที่ต้องจำ

- **`cloudReady()` เป็น `true` เสมอหลังเปิดแอป** แม้เน็ตจะหลุดไปแล้ว — โค้ดหลายที่ตัดสินใจจากค่านี้
  ต้องไล่แก้ให้ครบ ไม่ใช่แก้แค่จุดเดียว
- **`batch.commit()` ของ Firestore ไม่ resolve ตอนออฟไลน์** มันค้างเป็น pending จนกว่าจะต่อได้
  โค้ดที่ `await` อยู่จะค้างตามไปด้วย — `flushChanges()` มีตัวกัน (`pushing`) แล้วแต่ต้องทดสอบซ้ำหลังแก้
- **อย่าเชื่อคำว่า "Firebase ทำ offline ได้"** โดยไม่ตรวจว่าเปิด persistence แล้วหรือยัง
  (บทเรียนจากรอบนี้ — ผมเองก็ตอบผิดไปก่อนหน้านี้)
- **กล่องขาออกต้องจดตอน `write()` ไม่ใช่ตอนส่ง** ถ้าไปจดตอนส่ง (หน่วง 400 ms)
  แล้วแอปถูกปิดในช่วงนั้นพอดี งานจะไม่ถูกนับว่าค้าง แล้วหายเงียบ
- **`markPushed()` ต้องข้ามเอกสารในกล่องขาออก** ถ้าเผลอมาร์ก ระบบจะนึกว่าส่งไปแล้ว
  แล้วไม่ส่งอีกเลย = งานค้างอยู่ในเครื่องตลอดไป (พลาดง่ายมาก)
- **แคชรายชื่อคนขับในหน่วยความจำมีอายุ 5 นาที** ทำให้เทสล็อกอินออฟไลน์หลอกตัวเองได้
  ต้องเปิดแอปใหม่ก่อนเทส ไม่งั้นจะวิ่งเข้าทางออนไลน์โดยไม่รู้ตัว
- localStorage กับ IndexedDB **แยกตาม origin** `localhost` กับ `127.0.0.1` คนละชุดกัน
