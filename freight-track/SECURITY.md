# FreightTrack — รายงานตรวจความปลอดภัยและความสอดคล้องทางกฎหมาย

ตรวจเมื่อ: **20 ก.ย. 2026**
ขอบเขต: เว็บ FreightTrack (`StartUp/Shipment`) · Firebase โปรเจกต์ `REPLACE_WITH_YOUR_FIREBASE_PROJECT_ID` · Apps Script (`/exec`) · Google Sheet ทะเบียนคนขับ
วิธีตรวจ: อ่านโค้ดทั้งหมด + อ่านกฎ Firestore/Storage + **ยิงทดสอบจริงจากนอกระบบโดยไม่ล็อกอิน**

> ⚠️ **สถานะโดยรวม: ยังไม่พร้อมรับข้อมูลลูกค้าจริง**
> ไฟล์ `firestore.rules` ในโปรเจกต์เขียนเตือนตัวเองไว้แล้วว่า "ห้ามใช้กับข้อมูลลูกค้าจริง" — รายงานนี้ยืนยันว่าคำเตือนนั้นถูกต้อง

## 🔴 1. รหัสผ่านคนขับทุกคนเปิดให้คนนอกอ่านได้

**อาการ**
เว็บอ่านทะเบียนคนขับจาก Google Sheet ผ่าน gviz CSV **จากเบราว์เซอร์ของผู้ใช้โดยตรง**
(`js/driverSheet.js:18–20`) วิธีนี้บังคับให้ชีตต้องตั้งค่าเป็น "ทุกคนที่มีลิงก์ดูได้"
และรหัสชีตก็ฝังอยู่ในไฟล์ JavaScript ที่เสิร์ฟให้ทุกคนที่เปิดเว็บ

ชีตนั้นมีคอลัมน์ `B = PASSWORD` อยู่ด้วย

**หลักฐาน**
ยิงขอไฟล์ CSV ของชีตโดยไม่ล็อกอินบัญชีใด ๆ → ได้ข้อมูลกลับมาครบทุกคอลัมน์ รวมคอลัมน์รหัสผ่าน
รหัสที่เห็นเป็นค่าเริ่มต้นชุดเดียวกันทุกคน ซึ่งตรงกับค่า default ในโค้ด (`AppsScript-drivers.gs:128`)

**ผลกระทบ**
ใครก็ได้ที่เปิดเว็บแล้วกด View Source จะล็อกอินเป็นคนขับคนไหนก็ได้ แล้ว:
- กดปิดจุดส่งปลอม ทั้งที่ของยังไม่ถึง
- อัปรูปหลักฐานปลอม / เซ็นรับแทนผู้รับจริง
- ดูงานและที่อยู่ปลายทางทั้งหมดของบริษัท

หลักฐานการส่งของทั้งระบบจะใช้ยืนยันอะไรไม่ได้เลย ซึ่งกระทบถึงการวางบิลและการรับผิดเมื่อของหาย

**วิธีแก้**
ย้ายการตรวจรหัสผ่านไปไว้ฝั่ง Apps Script — เว็บส่ง ID + รหัสไปให้ตรวจ แล้วรับกลับมาแค่
"ผ่าน/ไม่ผ่าน" พร้อมโทเคนเซสชัน ไม่ต้องดึงทั้งชีตมาที่เครื่องผู้ใช้อีก
จากนั้น **ปิดการแชร์สาธารณะของชีต** และเก็บรหัสเป็นค่า hash ไม่ใช่ข้อความธรรมดา

> โค้ดเองเขียนข้อจำกัดนี้ไว้แล้วที่ `js/sheetAuth.js:12` ว่า "รหัสผ่านจึงไม่ใช่ความลับระดับธนาคาร"
> ของจริงหนักกว่านั้น คือไม่เป็นความลับเลย

## 🔴 2. ฐานข้อมูล Firestore เปิดอ่าน–เขียน–ลบ โดยไม่ต้องล็อกอิน

**อาการ**

```
firestore.rules
  match /{document=**} { allow read, write: if true; }
```

รหัสโปรเจกต์อยู่ใน `js/firebase.js` ซึ่งเปิดดูได้จากเบราว์เซอร์

**หลักฐาน**
เรียก Firestore REST API โดยไม่แนบการยืนยันตัวตนใด ๆ → อ่านข้อมูลคนขับจริงกลับมาได้
กฎเดียวกันนี้อนุญาตการเขียนและการลบด้วย

**ผลกระทบ**
คนนอกลบงานขนส่งทั้งระบบได้ในคำสั่งเดียว หรือแก้สถานะงาน/ค่ารอบ/คนขับได้ตามใจ
และ **ไม่มี log ว่าใครทำ** เพราะระบบยังไม่มีการยืนยันตัวตน

**วิธีแก้**
ทำ Firebase Auth แล้วเขียนกฎให้ตรวจ `request.auth`:
- คนขับ → เห็นและแก้ได้เฉพาะเที่ยวที่ตัวเองถูกจ่ายงาน
- แอดมิน → เห็นทั้งหมด (แยกด้วย custom claim)
- ลูกค้า (หน้าติดตาม) → อ่านได้เฉพาะเลขบิลที่ตัวเองถือ

## 🟠 3. Storage: ใครก็อัปไฟล์ได้ และรูปหลักฐานทุกใบเปิดสาธารณะ

**อาการ**

```
storage.rules
  match /evidence/{allPaths=**} {
    allow read: if true;                        ← ใครก็โหลดรูปได้
    allow write: if ขนาด < 5MB && เป็นรูปภาพ;   ← ไม่ตรวจว่าเป็นใคร
  }
}
```

**หลักฐาน**
ระหว่างทดสอบระบบเมื่อ 20 ก.ย. อัปไฟล์ขึ้นโฟลเดอร์ `evidence/` ได้สำเร็จโดยไม่ล็อกอิน
(ไฟล์ทดสอบถูกลบแล้ว) กฎกันได้แค่ "ไฟล์ต้องเป็นรูปและไม่เกิน 5 MB" เท่านั้น

**ผลกระทบ**
- รูปหลักฐานมี **ลายเซ็นผู้รับ ชื่อโรงพยาบาลปลายทาง และพิกัด GPS** — เปิดให้ใครก็โหลดได้ถ้ารู้ URL
- ใครก็ยัดรูปปลอมเข้าโฟลเดอร์หลักฐานได้ และ**ลบไม่ได้ด้วย** (ดูกับดักใน `STATUS.md` ข้อ 4)
- เสี่ยงถูกใช้เป็นที่ฝากไฟล์ฟรี ซึ่งตอนนี้จ่ายเงินจริงแล้วตั้งแต่ 20 ก.ย.

**วิธีแก้**
ปิด `allow read: if true` ให้ต้องผ่าน Auth · จำกัด write ตามสิทธิ์และ path ของเจ้าของงาน ·
แก้กฎให้รองรับการลบไปพร้อมกัน (เพิ่มเงื่อนไข `request.resource == null`)

## 🟠 4. API คนขับ (`/exec`) เปิดสาธารณะ ไม่มีรหัสลับ

**อาการ**
URL `/exec` ต้องเปิดสาธารณะเพราะ LINE webhook ต้องเรียกได้ แต่ฟังก์ชันอื่นในไฟล์เดียวกัน
ก็เปิดตามไปด้วย โดยไม่มีการตรวจสิทธิ์ใด ๆ

| ทาง | ทำอะไรได้ |
|---|---|
| `doGet` (`AppsScript-drivers.gs:53`) | คืน **ชื่อ–ทะเบียนรถ–เบอร์โทรคนขับทุกคน** เป็น JSON |
| `doPost` `action=upsert` (`AppsScript-drivers.gs`) | **เพิ่มหรือแก้คนขับได้ โดยไม่ตรวจอะไรเลย** |

**ผลกระทบ**
คนนอกเพิ่มคนขับปลอมเข้าระบบได้ หรือแก้เบอร์โทร/ทะเบียนของคนขับจริง
และดึงรายชื่อพนักงานขับรถทั้งบริษัทไปใช้ต่อได้

> ข้อดีที่ทำถูกแล้ว: `doGet` **ไม่คืนคอลัมน์รหัสผ่าน** (ตั้งใจข้าม) — แต่ช่องโหว่ข้อ 1 ทำให้ไม่ช่วยอะไร

**วิธีแก้**
เพิ่มรหัสลับร่วม (shared secret) ใน body ของทุกคำขอที่ไม่ใช่ LINE webhook แล้วเก็บรหัสนั้นไว้ใน
Script properties · ส่วน `doGet` ควรต้องแนบรหัสเช่นกัน หรือตัดออกถ้าไม่ได้ใช้แล้ว

## 🟠 5. LINE webhook ไม่ตรวจลายเซ็น

**อาการ**
ไม่มีการตรวจ `x-line-signature` ตามที่ LINE กำหนด — โค้ดยอมรับข้อจำกัดนี้ไว้เองที่
`AppsScript-lineIntake.gs:36` ว่าความปลอดภัยอยู่ที่ "ลิงก์ `/exec` เดาไม่ได้" เท่านั้น

**ผลกระทบ**
ถ้า URL หลุด (อยู่ใน `STATUS.md` และในการตั้งค่า LINE Developers) คนนอกยิง webhook ปลอมเข้ามาได้
ทำให้ระบบประมวลผลไฟล์ที่ไม่ได้มาจากลูกค้าจริง

**วิธีแก้**
Apps Script อ่าน header ไม่ได้ตรง ๆ จึงควรย้ายจุดรับ webhook ไปไว้ที่ Cloud Functions หรือ
Cloud Run ที่ตรวจ HMAC-SHA256 ด้วย Channel secret ได้ แล้วค่อยส่งต่อเข้า Apps Script
(ถ้ายังไม่ย้าย อย่างน้อยควรตรวจ `destination` ให้ตรงกับ Channel ID ของเรา)

## 🟡 6. ไม่มี log และไม่มีทางรู้ตัวว่าถูกละเมิด

ระบบไม่ได้เก็บว่าใครเข้าถึงอะไรเมื่อไหร่ และไม่มีการแจ้งเตือนเมื่อมีพฤติกรรมผิดปกติ
ทำให้ถ้าเกิดเหตุจริงจะ **ไม่รู้ว่าเกิดขึ้นแล้ว ไม่รู้ว่าข้อมูลใดหลุด และบอกไม่ได้ว่าใครทำ**
ซึ่งกระทบโดยตรงต่อหน้าที่แจ้งเหตุภายใน 72 ชั่วโมงตาม PDPA และหน้าที่เก็บ log ตาม พ.ร.บ.คอมพิวเตอร์

**เรื่องที่เกี่ยวข้องและควรรู้ไว้:** `js/cloud.js` ออกแบบให้ **กลืน error ตอนอัปรูปไม่สำเร็จ**
แล้วถอยไปเก็บ base64 ในเครื่องเงียบ ๆ — ดีตรงที่หลักฐานไม่หาย แต่แปลว่าระบบล่มได้โดยไม่มีใครรู้
(เกิดขึ้นจริงมาแล้ววันที่ 20 ก.ย. ดู `STATUS.md` ข้อ 4.1) ควรมีสัญญาณเตือนฝั่งแอดมิน

## ✅ ของที่ทำถูกแล้ว

- **ป้องกัน XSS ได้ดี** — `esc()` ใน `js/ui.js` เป็นตัว escape ที่ถูกต้อง และถูกใช้สม่ำเสมอทั้งใน
  `toast` / `modal` / `confirmDialog` / รายการคนขับ / ตารางงาน ทั้งที่ข้อมูลจำนวนมากมาจากไฟล์ Excel ของลูกค้า
- **โทเคนลิงก์คนขับภายนอกใช้ `crypto.getRandomValues`** ไม่ใช่ `Math.random` — เดาไม่ได้จริง (`js/store.js` `randToken`)
- **LINE Channel access token อยู่ใน Script properties** ไม่ฝังในโค้ด
- **`doGet` ไม่คืนคอลัมน์รหัสผ่าน** — ตั้งใจข้ามคอลัมน์ B
- ไม่มีไฟล์ความลับ (`.env`, `credentials.json`, service account) หลุดอยู่ในโฟลเดอร์โปรเจกต์
- กฎ Storage จำกัดชนิดไฟล์และขนาดไว้แล้ว (แม้จะยังไม่ตรวจตัวตน)

> **หมายเหตุ: `apiKey` ใน `js/firebase.js` ไม่ใช่ช่องโหว่**
> ค่านี้เป็นตัวระบุโปรเจกต์ที่ Firebase ออกแบบมาให้เปิดเผยในโค้ดฝั่งเบราว์เซอร์อยู่แล้ว
> ความปลอดภัยทั้งหมดอยู่ที่ Rules ไม่ใช่การซ่อน key — ซึ่ง Rules คือปัญหาในข้อ 2 และ 3

### ข้อมูลส่วนบุคคลที่ระบบนี้เก็บ

| ประเภท | ตัวอย่างในระบบ |
|---|---|
| ข้อมูลพนักงาน | ชื่อ–นามสกุล เบอร์โทร ทะเบียนรถ รหัสผ่าน |
| ข้อมูลตำแหน่ง | **พิกัด GPS ของคนขับระหว่างวัน** + พิกัดตอนปิดจุดส่ง |
| ข้อมูลผู้รับ | ชื่อผู้รับ **ลายเซ็น** ชื่อและที่อยู่สถานที่จัดส่ง เบอร์ติดต่อ |
| ข้อมูลธุรกิจของลูกค้า | รายการยา ปริมาณ มูลค่า ปลายทาง |

### PDPA (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562)

| ประเด็น | สถานะปัจจุบัน |
|---|---|
| **ม.37(1)** ต้องจัดให้มีมาตรการรักษาความมั่นคงปลอดภัยที่เหมาะสม | ❌ ช่องโหว่ข้อ 1–4 คือหลักฐานว่ายังไม่มี |
| **ม.37(4)** ต้องแจ้งเหตุละเมิดต่อสำนักงาน (สคส.) ภายใน **72 ชั่วโมง** | ⚠️ ทำไม่ได้จริง เพราะไม่มีระบบรู้ตัว (ข้อ 6) |
| **ม.19** ต้องมีฐานทางกฎหมายและแจ้งวัตถุประสงค์ | ⚠️ การติดตาม GPS พนักงานทั้งวันต้องแจ้งให้ชัดและมีฐานรองรับ การอ้าง "สัญญาจ้าง" อย่างเดียวอาจไม่พอ |
| **ม.40** หน้าที่ของผู้ประมวลผลข้อมูล | ⚠️ ข้อมูลผู้รับ/โรงพยาบาลมาจากลูกค้า ลูกค้าน่าจะเป็น Data Controller ส่วนบริษัทเป็น Processor → ควรมีข้อตกลงประมวลผลข้อมูล (DPA) ก่อนเริ่มงานจริง |
| การเก็บข้อมูลเท่าที่จำเป็น | ⚠️ ควรกำหนดอายุการเก็บรูปหลักฐานและพิกัด ไม่ใช่เก็บตลอดไป |

### พ.ร.บ.ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์

- **ม.26** ผู้ให้บริการต้องเก็บข้อมูลจราจรทางคอมพิวเตอร์ไม่น้อยกว่า **90 วัน** — ปัจจุบันยังไม่ได้เก็บ

### ข้อควรระวังเฉพาะธุรกิจนี้

ลูกค้าคือโรงพยาบาล ของที่ขนส่งคือยาและเวชภัณฑ์ ข้อมูลว่าส่งยาอะไรไปโรงพยาบาลไหนปริมาณเท่าไร
เป็นข้อมูลที่ลูกค้าอาจถือว่าอ่อนไหวเชิงธุรกิจ และ **หากมีชื่อผู้ป่วยหลุดเข้ามาในช่องหมายเหตุเมื่อใด
จะกลายเป็นข้อมูลอ่อนไหวตาม ม.26 ของ PDPA ทันที** ซึ่งมีบทลงโทษหนักกว่าข้อมูลทั่วไปมาก
ควรมีการตรวจและกันไม่ให้ข้อมูลประเภทนี้เข้าระบบตั้งแต่ขั้นนำเข้าไฟล์

## แผนแก้ตามลำดับความสำคัญ

| ลำดับ | งาน | ปิดช่องโหว่ข้อ | ความยาก |
|---|---|---|---|
| 1 | ย้ายการตรวจรหัสผ่านไปฝั่ง Apps Script แล้วปิดการแชร์ชีตสาธารณะ | 1 | ไม่กี่ชั่วโมง |
| 2 | เปลี่ยนรหัสคนขับทุกคนจากค่าเริ่มต้น + บังคับตั้งใหม่ครั้งแรก | 1 | ครึ่งวัน |
| 3 | ทำ Firebase Auth แล้วรัด `firestore.rules` ตามบทบาท | 2 | 2–3 วัน |
| 4 | รัด `storage.rules` ให้ต้องผ่าน Auth + แก้เรื่องลบไฟล์ | 3 | ครึ่งวัน (ทำพร้อมข้อ 3) |
| 5 | ใส่รหัสลับร่วมใน `/exec` + ตรวจ `destination` ของ LINE | 4, 5 | ครึ่งวัน |
| 6 | เก็บ log การเข้าถึง 90 วัน + แจ้งเตือนเมื่ออัปรูปไม่สำเร็จ | 6 | 1–2 วัน |
| 7 | ร่างนโยบายความเป็นส่วนตัว + DPA กับลูกค้า + กำหนดอายุการเก็บข้อมูล | กฎหมาย | ต้องมีที่ปรึกษา |

**ข้อ 1–4 คือเส้นแบ่งว่าระบบพร้อมรับข้อมูลลูกค้าจริงหรือยัง** ก่อนทำครบไม่ควรนำข้อมูลจริงของโรงพยาบาลเข้าระบบ
